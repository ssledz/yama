Features

Small on purpose, complete anyway

The loop itself is 45 lines. Everything below is plumbing around it, and each piece is one small, swappable brick.

the loop

A visible agentic loop

Send the conversation, run the tools the model asked for (in parallel, parTraverse), append the results, repeat. Stops on a final answer or after maxRounds.

observability

Verbose log of every round

Each model call with its token cost, each tool call with arguments and result, and the nested loop of a worker agent, indented under its name.

providers

OpenAI, OpenRouter, DeepSeek, Ollama

One component speaks the OpenAI Responses API, stateless. A provider is data in config.json; switch with --provider, no code change.

native tool

wget

Downloads any URL into the workspace or session folder, with a sandbox check. Its JSON Schema is derived from a case class at compile time: derives ToolSchema.

local MCP

Sandboxed files server

fs_read, fs_search, fs_write, fs_manage from @ssledz/files-mcp, spawned over stdio with the fs2 process API.

remote MCP

Streamable HTTP + Bearer auth

Remote MCP servers such as Tavily web search, behind the same McpClient[F] as the local one. The model can't tell native, local or remote tools apart.

resilience

MCP supervisor

A crashed local server is respawned and re-initialised with exponential backoff; calls made during the restart wait for it. Gives up after 5 quick crashes in a row.

agent skills

Skills, loaded on demand

Implements the Agent Skills format: catalog in the prompt, body via activate_skill, files via read_skill_resource. Built-in skills ship inside the jar.

multi-agent

Subagents as tools

Orchestrator–worker: research_agent is a whole agent behind a tool, with its own prompt, tools, model and round budget, and a fresh conversation per call.

guardrails

Least privilege by construction

The agent writes to exactly two mounts: the workspace and a per-run session folder. Tools are chosen per agent. Round budgets everywhere, and subagent depth is 1.

reliability

Retries outside the loop

429 and 5xx are retried by Chat.retrying (cats-retry): exponential backoff, full jitter, capped, honouring Retry-After. Tool failures are data the model recovers from.

distribution

One executable file

A fat jar with a launcher in front: chmod +x yama && ./yama. First run writes its config to ~/.yama. Version baked in: yama --version.

code

Tagless final, Cats Effect 3

Every component is polymorphic in F[_]; IO appears in one file. http4s, circe, fs2, ciris, decline, log4cats, cats-retry, MCP Java SDK.

architecture

Polylith on sbt

12 components, 1 base, 1 project. Bricks depend on interfaces only; implementations are private[brick] and a CI script guards the boundaries.

tests

Deterministic agent tests

ScriptedChat replays model replies, so the loop is fully testable. Golden-JSON wire tests, a real MCP integration test, supervisor tests. munit + CE.

Install

Download, set a key, run

yama ships as one executable file from GitHub releases. You need JDK 21+ to run it, Node 20+ (for npx, which starts the files MCP server), and an API key for one LLM provider.

  1. Download the executable

    The latest release, made executable:

    curl -fLo yama https://github.com/ssledz/yama/releases/latest/download/yama
chmod +x yama
./yama --version

    No stable release yet, or want the bleeding edge? Grab yama from the vX.Y.Z-SNAPSHOT pre-release on the releases page. It is also a plain jar: java -jar yama works on any OS.

  2. Put your API key in the environment

    Secrets come only from env vars, never from the config file. Only the selected provider's key is required (OpenAI by default):

    export OPENAI_API_KEY=sk-...           # default provider
export TAVILY_API_KEY=tvly-...         # optional: enables research_agent (web search)

    Keep them in a .env file? The JVM doesn't read it: set -a; source .env; set +a, or use direnv.

  3. Run it in the directory it should work in

    The directory you start yama in is its workspace: the only place (besides its session folder) it may write to.

    mkdir demo && cd demo
../yama

yama> download https://example.com and save a short summary as example.md
yama> research what Art of Scala 2026 is about and save a short summary as aos.md

    The first run creates ~/.yama/config.json from the defaults bundled in the jar. The second instruction needs TAVILY_API_KEY.

Or build from source

Needs JDK 21+, sbt and Node 20+.

git clone https://github.com/ssledz/yama && cd yama
npm install --prefix mcp/files-mcp        # the local MCP server (TypeScript)
sbt "yama-cli/run --config config.json"   # run against the repo's config
sbt yama-cli/assembly                     # → projects/yama-cli/target/scala-3.*/yama.jar

Configuration

Where the config lives, and how to change it

Everything except secrets is in one JSON file. Secrets come only from env vars. Command-line flags beat env vars, which beat the file.

yama's home directory

Resolved in this order:

#source
1--config-dir <dir>
2$YAMA_CONFIG_DIR
3~/.yama (default)
~/.yama/
├── config.json        read when --config is not given
├── skills/            your user-level skills
└── sessions/
    └── -Users-me-demo/  one folder per workspace
        └── 20261124-093015-3fa9c2/  one per run

The config file

  • First run: ~/.yama/config.json is created from the defaults bundled in the jar. With npx on the PATH, its files server runs the published @ssledz/files-mcp, pinned to the version built with this yama.
  • It is yours after that: new releases never overwrite it. Delete it to get fresh defaults on the next run.
  • Another file: --config path/to/config.json. A --config that doesn't exist is an error, never created. Relative paths inside a config file resolve against that file's directory.
  • Session folder: created only when the agent first writes into it; a run that writes nothing leaves nothing behind.

What's in config.json

keywhat it controls
chatthe selected provider and model, and the retry policy (maxAttempts, baseDelayMs, maxDelayMs)
providersone profile per provider: baseUrl, apiKeyEnv (the name of the env var holding the key), extra headers, capability flags such as strictTools
agentthe system prompt (instructions), maxRounds, and mcpServers: which servers' tools the orchestrator gets. Placeholders {{MOUNT}}, {{SANDBOX_DIR}}, {{SESSION_MOUNT}}, {{SESSION_DIR}} are substituted
sandboxdir: the workspace, if not the directory yama runs in
mcpServersno type: a local process over stdio (command, args, cwd, env). "type": "http": a remote server (url, headers, apiKeyEnv sent as Authorization: Bearer; skipped when the key is unset)
skillsextra skill paths and trustProject (load skills from the project's .yama/skills and .agents/skills)
subagentsworker agents exposed to the orchestrator as tools: description, instructions, tools (by name), optional model, maxRounds

Common changes

switch provider or model

For one run, use a flag or env var:

./yama --provider openrouter --model openai/gpt-4.1
YAMA_PROVIDER=ollama YAMA_MODEL=qwen3 ./yama

For good, edit chat in ~/.yama/config.json:

"chat": {
  "provider": "openrouter",
  "model": "openai/gpt-4.1"
}
add a provider

Any service exposing POST {baseUrl}/responses works, no code needed:

"providers": {
  "mine": { "baseUrl": "https://llm.example.com/v1",
            "apiKeyEnv": "MY_LLM_KEY" }
}

Then --provider mine with MY_LLM_KEY exported.

add an MCP server

Add it under mcpServers, then list its name in agent.mcpServers to give its tools to the agent:

"mcpServers": {
  "git": { "command": "uvx",
           "args": ["mcp-server-git"] }
},
"agent": { "mcpServers": ["files", "git"], ... }
add a skill

Drop a folder with a SKILL.md into ~/.yama/skills/ (or the project's .yama/skills/). It shows up in /skills on the next start.

~/.yama/skills/commit-message/SKILL.md
---
name: commit-message
description: How to write a commit message. Use when ...
---
# Instructions ...

Command-line flags

flagmeaning
--config-diryama's home (default $YAMA_CONFIG_DIR, else ~/.yama)
--configconfig file (default <config-dir>/config.json)
--providerprovider profile: openai, openrouter, deepseek, ollama
--modelmodel id, e.g. gpt-4.1
--sandboxworkspace directory (default: the current one)
--max-roundsround budget of the orchestrator
--skills-pathextra skills directory (repeatable)
--version, --help

Environment variables

variablemeaning
OPENAI_API_KEYOpenAI key (default provider)
OPENROUTER_API_KEYOpenRouter key; pick a model with tool support
DEEPSEEK_API_KEYDeepSeek key
OLLAMA_API_KEYoptional; Ollama ≥ 0.13.3 needs no key
TAVILY_API_KEYweb search for research_agent; without it the worker is disabled
YAMA_PROVIDER, YAMA_MODELoverride chat.provider / chat.model
YAMA_CONFIG_DIRyama's home instead of ~/.yama

Precedence: CLI flag > env var > config.json. Config errors are reported all at once, before the REPL starts. API keys are redacted wherever they would be printed.

Using it

The REPL

Type an instruction in plain language, or a command. /history is the interesting one: it is the raw conversation the model sees, which is all the memory an agent has.

commandwhat it does
/helplist commands
/toolsthe tools the agent can call, and where each lives (native, mcp:files, skill, agent)
/promptthe system instructions after placeholder substitution, with the skills catalog
/historythe raw conversation, including tool calls and results
/statstoken usage so far, per agent
/skillsdiscovered skills and discovery diagnostics
/skill <name> <instruction>run an instruction with a skill pre-loaded
/resetforget the conversation, reset counters
/exitquit (ctrl-d works too)
